Scenarios

Can a one-line description of a historical event become a scenario you can play?

Authoring a campaign-quality Age of Empires II scenario takes hours of work in an idiosyncratic editor and fluency in the history it depicts, so most historical events are simply absent from the game. We turn scenario authoring into code generation against a game-modding API: an episode specification goes in, and a .aoe2scenario file a player can load in the shipped game comes out.

Input
Episode specification

A title, a two-to-three sentence description, a scenario type drawn from six categories (battle, escort, defense, conquest, diplomacy, story), and optional region and civilization hints. Those six fields are the entire input.

Generator
LLM writes Python

A compositional system prompt is assembled from the scenario type's template and optional conditioning blocks, and the model emits Python against the open-source AoE2ScenarioParser API — units, terrain, players, and triggers as Python objects.

Output
A playable scenario file

Validated against structural preconditions, executed in an isolated subprocess, and repaired on failure — up to three times — before the resulting file is confirmed to load back through the parser.

↓
The key mechanism
Introspection-guided self-repair

AoE2ScenarioParser is thinly represented in model training data, so the dominant failure class is API misuse: importing an enum member that does not exist, calling a real method with the wrong signature, naming a module that was never there. For ImportError, AttributeError, TypeError, NameError and ModuleNotFoundError, the generator does not merely relay the error message. It introspects the installed library at repair time and injects ground truth into the repair prompt: the module's real exports, the closest matches to the name the model invented, or the true signature of the method it miscalled. Repair therefore corrects against the API surface that will actually execute the code.

Abstract

Historical strategy games are one of the most widely used informal channels through which people encounter the past, and research in the learning sciences suggests that playing them can produce durable historical understanding. The history a player can actually inhabit, however, is limited to the scenarios someone has built: authoring a single campaign-quality scenario for a game like Age of Empires II demands hours of work and simultaneous fluency in the history and in an idiosyncratic editor, so most historical events are simply absent. We address this authorship bottleneck, generating complete playable scenarios from a short natural-language description of a historical event, so that an educator can produce a scenario for exactly the episode a lesson needs. Our pipeline prompts a large language model to write Python against an open-source scenario-file API and executes the result, backed by an introspection-guided self-repair loop that grounds error correction in the installed library's real API surface, and a fully automated evaluation in which build success and playability are machine-checked and historical fidelity is scored against a rubric by an LLM judge validated with a mismatch control. Over eight historical episodes, 31 of 32 runs produced a scenario that loads in the shipped game and a static audit found none unwinnable. Our main result separates two kinds of knowledge that a single quality score conflates. Stating the fidelity criteria in the generator's own prompt moves the dimensions where content is a choice, but the weakest dimension in the study — the setting a scenario depicts — proved bounded by API knowledge instead: two thirds of its gain arrived with three lines of extracted API fact rather than with any instruction about history, and those same lines took first-attempt builds from zero of eight to eight of eight. The effect replicates on eight held-out episodes. We release the generator, prompts, rubric, and evaluation harness.

The dissociation: capability, not instruction

A generative system pointed at a niche API is solving two problems that look like one from the outside: knowing what the artifact should contain, and knowing how to make the library produce it. Restricting to the seven episodes that carry all three arms, the two dimensions come apart. Combatants — naming the right commander — moves +1.00 on the rubric alone and a further +0.24 on the API facts: stating the criterion is 81% of the fix. Setting moves +0.62 on the rubric and a further +1.19 on the API facts: two thirds of the gain arrives with the facts, not the instruction. All 31 baseline scenarios leave every player at RANDOM, so architecture, player names, and civilization bonuses are drawn by the game at load time rather than by the generator. The model did not know the API well enough to set one field, and no amount of instruction about material culture addressed it.

Playability is machine-checked

Code that runs is not the same as a scenario that can be won. A victory condition keyed to "zero enemy units remain in this area" becomes permanently unreachable the moment one enemy unit garrisons a building or flees the region, stranding the player in a scenario that cannot be completed — a failure no syntax check or successful build will ever surface. A deterministic static analysis reads each built scenario back through the parser and checks for a missing victory or defeat path, a fragile victory, a degenerate victory, and orphan triggers that ship disabled. No scenario in any condition was unwinnable. 

# Fragile: unwinnable if one enemy
# garrisons, converts, or flees.
vc.new_condition.objects_in_area(
    quantity=0, ...)

# Deterministic: fires when that
# object dies.
leader = unit_manager.add_unit(
    PlayerId.TWO,
    unit_const=HeroInfo.GENGHIS_KHAN.ID, ...)
vc = trigger_manager.add_trigger("VC")
vc.new_condition.destroy_object(
    unit_object=leader.reference_id)
vc.new_effect.declare_victory(
    source_player=PlayerId.ONE, enabled=1)

The victory-condition idiom taught by the reachability block: prefer destroy_object on a stored unit reference over objects_in_area(quantity=0).
